# Changement de contexte

Un changement de contexte fait passer un CPU d'un thread à un autre. Les registres du thread qui part sont sauvegardés là où le noyau pourra les retrouver, en général sur la propre pile de ce thread ou dans son bloc de contrôle ; le pointeur de pile est dirigé vers l'état sauvegardé du thread qui arrive, et ses registres sont restaurés, si bien qu'il reprend exactement là où il s'était arrêté. Les noyaux arrivent à un changement par deux voies. Un changement involontaire se produit sur une interruption : l'entrée de l'interruption a déjà sauvegardé les registres du thread interrompu, si bien que le noyau n'a plus qu'à revenir dans un autre état sauvegardé. Un changement volontaire se produit quand un thread appelle le noyau pour se bloquer ou céder la main, par une routine qui sauvegarde elle-même les registres.

Un changement coûte plus que les registres qu'il copie. Le thread qui arrive trouve les caches et les tampons de traduction d'adresses remplis des données de l'autre thread, et s'exécute plus lentement jusqu'à ce qu'il les ait de nouveau réchauffés ; c'est pourquoi un ordonnanceur ne change pas de thread plus souvent que sa politique ne l'exige.

Le piège, c'est que décider de changer et changer sont deux étapes distinctes. Un ordonnanceur peut décider pendant un tick, ou quand un thread est réveillé, alors que le changement lui-même n'a lieu que quand le noyau quitte l'interruption. Tout ce qui se trouve entre la décision et le changement doit s'accorder avec elle : le thread enregistré comme courant, le thread remis dans la file et la pile que le CPU va reprendre doivent tous décrire le même changement, sans quoi le CPU reprend un thread que la comptabilité place ailleurs.

Dans Cosmos, chaque changement a lieu à une sortie d'interruption. Le stub d'interruption sauvegarde les registres du thread, état SIMD compris, sur la pile du thread ; le gestionnaire appelle `PickNext`, consigne dans le `SchedulerThread.StackPointer` de l'ancien thread l'endroit où se trouve son état et prépare celui du nouveau, à partir duquel le stub restaure en sortant. La première exécution d'un thread, qui n'a aucun cadre sauvegardé dans lequel revenir, saute plutôt à son point d'entrée. La sortie de n'importe quelle interruption peut porter un changement : le tick du minuteur quand `OnTick` renvoie `true`, et toute interruption matérielle dès qu'un réveil, un blocage, un `Thread.Yield` ou un remplacement de politique a demandé un réordonnancement, auquel cas `PickNext` s'exécute quoi qu'ait répondu `OnTick`, ou sans passer du tout par `OnTick` quand l'interruption n'est pas le tick. Il n'y a pas de changement volontaire : un thread qui se bloque déclenche une interruption sur son propre CPU pour le quitter (le thread inactif s'arrête à la place), et `Thread.Yield` revient immédiatement en laissant le changement à la prochaine sortie d'interruption. La politique ne touche jamais un registre. Voir [Le tick](../scheduler.md#the-tick) et [Ce qui n'existe pas : un changement volontaire](../scheduler.md#what-there-is-not-a-voluntary-switch).
