# États des threads et file d'exécution

À tout instant, un thread se trouve dans l'un de quelques états. Il est en cours d'exécution pendant qu'un CPU l'exécute, prêt quand il pourrait s'exécuter mais qu'aucun CPU n'est libre pour lui, et bloqué tant qu'il attend quelque chose : un verrou, un périphérique, un signal, ou un instant donné, que certains noyaux suivent comme un état d'endormissement distinct. Un nouveau thread commence à l'état créé et devient prêt quand il est démarré, et un thread terminé reste mort jusqu'à ce que le noyau le récupère. Seuls les threads prêts se disputent le CPU, et l'ordonnanceur les garde dans sa file d'exécution. Le nom est traditionnel : la structure peut être une FIFO, une liste triée selon une clé, un tas, ou une file par niveau de priorité, tout ce qui rend peu coûteux, pour la politique, le choix du thread suivant.

Un CPU doit toujours exécuter quelque chose : quand aucun thread n'est prêt, il exécute donc un thread inactif, qui en général arrête le cœur jusqu'à la prochaine interruption. Un thread inactif ne doit jamais se bloquer, car il n'y a rien derrière lui sur quoi se replier.

Le piège, c'est le thread en cours d'exécution. Qu'il reste dans la file d'exécution pendant qu'il s'exécute, ou qu'il en soit retiré quand il est choisi et remis quand il quitte le CPU, relève d'une convention, et un code qui mélange les deux conventions met un thread deux fois en file ou le perd. Un thread mis deux fois en file obtient deux tours, et dans une file triée, une entrée périmée qui garde sa place casse l'ordre pour tous les threads situés derrière elle. Un thread perdu par la file reste prêt sans jamais être choisi, ce qui, vu de l'extérieur, ressemble à un noyau figé.

Dans Cosmos, les états sont ceux de `SchedulerThreadState` : `Created`, `Ready`, `Running`, `Blocked`, `Sleeping` et `Dead`, et une politique ne les modifie jamais. Le thread en cours d'exécution n'est normalement pas dans la structure de la file d'exécution : `PickNext` retire le thread qu'il renvoie, et le thread qui quitte le CPU revient par `OnThreadYield` après le choix, seulement s'il était encore `Running`. L'exception est un thread qui s'est bloqué et a été réveillé avant que le changement de contexte ne le retire du CPU : il est `Ready` et en file alors qu'il s'exécute encore. Un réveil pour un thread déjà `Ready` ou `Running` ne fait rien, mais un thread `Created` garde cet état jusqu'à sa première exécution, si bien que `OnThreadReady` peut arriver deux fois pour lui et doit se prémunir contre une seconde insertion. Le thread inactif est le thread de démarrage lui-même, celui qui appelle ensuite `BeforeRun` et `Run` du noyau. Quand `PickNext` renvoie `null`, c'est lui qui s'exécute, quel que soit son état. Le mutex du noyau, son événement d'interruption et sa variable de condition, cette dernière étant derrière les attentes propres de CoreLib (`Thread.Sleep`, `Thread.Join`, un `WaitHandle`) par son moniteur bas niveau, le font tourner en boucle, scruter ou arrêter le cœur entre deux vérifications au lieu de se mettre en attente, si bien qu'il n'atteint jamais `OnThreadBlocked` : un thread inactif mis en attente reviendrait par le repli à l'état `Running`, sans le réveil qui lui rend ses tickets. Pour le reste, il passe par les hooks comme n'importe quel autre thread : il atteint `OnThreadCreate` déjà `Running` quand une politique est installée, et revient par `OnThreadYield` quand il est retiré du CPU. Voir [Cycle de vie](../scheduler.md#lifecycle) et [L'interface](../../user/scheduler-plugging.md#the-interface).
