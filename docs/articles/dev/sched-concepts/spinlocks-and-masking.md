# Spinlocks and interrupt masking

A spinlock protects data from code running on another CPU: a thread that finds the lock taken loops until the holder releases it. That works because the holder keeps running on its own CPU while the other one spins. It does not work against an interrupt handler on the same CPU. If the handler fires while the code it interrupted holds the lock, and tries to take the lock itself, it spins, and the holder cannot release the lock until the handler returns, so the CPU spins forever.

Code that shares data with an interrupt handler therefore masks interrupts on its CPU around each access, so the handler cannot fire in the middle of it. Masking is the only protection a CPU needs against its own interrupts, but a spinlock is still needed against other CPUs, so kernels combine the two in an interrupt-safe lock: mask, then take the lock; release, then restore. Masking saves the previous interrupt state and restores it, rather than turning interrupts back on, so one masked section can sit inside another.

The trap is code that takes no lock. A lock only excludes code that takes the same lock, and an interrupt handler that touches the data without taking it, often because it is not allowed to wait, is not kept out by any lock the thread side holds. Only masking keeps that handler out. Masking also makes exactly one section atomic: a caller that reads a count in one masked call and then walks the items in further calls can see the structure change between them.

The opposite trap is a mask that stands in for a lock. A mask excludes the interrupts of the CPU that masked and nothing else: a thread on another CPU walks straight into the section, since nothing it does looks at this CPU's interrupt flag. On one CPU the two are indistinguishable, which is how the ring and the HAL came to guard the keyboard queue, the session table, the timer registry and the network device table with a mask alone, each written while every thread ran on CPU 0. A mask is enough for state only the masking CPU touches (its own per-CPU record), and for giving a handler the masked context every source promises it (`Ps2Access` delivering a polled byte); anything a thread on another CPU can reach, a queue a handler fills and a thread drains, a table a worker writes and a reader scans, a registry a tick walks and a caller grows, takes a lock, and since the handler side needs the mask as well, the interrupt-safe spinlock (SMP phase 4b, [#3347](https://github.com/CosmosOS/Cosmos/issues/3347)).

In the Cosmos scheduler, each CPU's run structure is guarded by that CPU's queue lock, an interrupt-safe spinlock in its `PerCpuState` (SMP phase 3a, [#3340](https://github.com/CosmosOS/Cosmos/issues/3340)). The mechanism holds it around every policy hook that touches the structure: the owning CPU takes it from its tick (`OnTick`) and from the interrupt exit that reschedules (`PickNext`, `OnThreadYield`), where interrupts are masked already, and a thread on any CPU takes it, with its own interrupts masked, to wake a thread onto that CPU or to take one off it (`OnThreadReady`, `OnThreadBlocked`, `OnThreadExit`, `SetPriority`, `GetPriority`, the two run-queue diagnostics). So a hook never takes the lock itself: it is not re-entrant, and the manager already holds it. The three hooks that run under no lock, `OnThreadCreate`, `InitializeCpu` and `ShutdownCpu`, are the ones that may allocate, because nothing allocates under a spinlock: an allocation can collect, and a collection stops every other CPU for its duration; a CPU that spins on a spinlock with interrupts masked answers that stop from inside its spin, so a waiter never holds a collection up, but a CPU holding one of the locks the collector itself takes (the heap lock, the handle store's, the page allocator's) cannot answer until it releases, and a holder that collected would wait for it. The kernel forbids allocation under every spinlock rather than reason about it lock by lock, and a collection started by a CPU that holds one of those three locks is a panic naming the caller ([Stopping the world](../garbage-collector.md#stopping-the-world)). An entry point a policy adds of its own locks through `SchedulerManager.LockCpu(state)`, whose `CpuLockScope` masks and locks until it is disposed; a caller that walks a run queue through the diagnostics hooks holds that scope around the whole walk, since each hook alone is atomic and the walk is not. The locks are taken in one order, queue locks by ascending CPU index, then the thread registry's lock, then the stop, then the heap's, and two queue locks at once only by a migration. See [SpinLock and the IRQ-safe scope](../scheduler.md#spinlock-and-the-irq-safe-scope) and [Kernel constraints](../../user/scheduler-plugging.md#kernel-constraints).

The locks of the ring and the HAL sit outside that order (SMP phase 4b, [#3347](https://github.com/CosmosOS/Cosmos/issues/3347)). A session's lock (its screen, its colours and cursor, its input ring), the keyboard queue's, the tick source's and the network table's are each taken last, a session's before its screen's; the session manager's is taken before a session's and the keyboard queue's, which the drain at the routing hand-over takes inside it, and before a screen's, which a switch takes inside it. None is taken under a scheduler lock, and none is held across a call into the scheduler: the drain queues the waiting keys under the manager's lock and wakes the session's reader once it has released it. Nothing allocates under any of them, for the reason above: what a member installs is allocated before the lock and dropped when another thread won, a snapshot is taken into an array sized before the lock, a full registry grows outside the lock and the registration is retried, a screen's new grid is allocated before the resize takes the locks, and a queue a handler fills is a fixed ring rather than one that grows, the session's dropping the key past its capacity and the keyboard's overwriting its oldest.
