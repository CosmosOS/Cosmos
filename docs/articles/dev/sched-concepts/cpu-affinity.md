# CPU affinity and load balancing

On a machine with several CPUs, a scheduler usually gives each CPU its own run queue. A single shared queue would need a lock that every CPU contends for on every switch, and a thread that keeps returning to the same CPU finds its data still in that CPU's caches. Per-CPU queues bring two decisions of their own. Placement picks a CPU for a thread when it is created or woken, typically the least loaded one. Load balancing moves threads afterwards, when one queue runs long while another CPU sits idle: the idle CPU pulls, or steals, a thread from a busy one, or a busy CPU pushes one away.

Affinity limits where a thread may go. Hard affinity, or pinning, restricts a thread to one CPU or a set of them, for a per-CPU thread such as an idle thread or for code that touches per-CPU state. Soft affinity is only a preference, the cache warmth a scheduler weighs against the load.

The trap is per-CPU state that travels with the thread. A policy that keeps a per-CPU clock, such as the virtual time of a [fair-share](virtual-time-fair-share.md) scheduler, has to rebase a migrating thread on the destination's clock, or the thread arrives far ahead of or far behind every thread there. A migration also touches the queues of two CPUs at once, so it has to be safe against the ticks of both, and a balancer must never steal a thread whose set excludes it.

## The model in Cosmos

A thread carries a hard set and an ideal CPU (SMP phase 3b, [#3341](https://github.com/CosmosOS/Cosmos/issues/3341)). `SchedulerThread.Affinity` is a `CpuSet`, 256 bits in four words, never empty: the CPUs the thread may run on. `IdealCpu` is the policy's preference, always inside the set: the CPU the thread was created on until a kernel sets it, and the CPU the thread goes to when a set change excludes it, which is what Windows does with its ideal processor. There is no pinned flag: a pinned thread is a set naming one CPU, and the idle threads are each pinned to their own. The set is written under the queue lock of the thread's CPU and read under it wherever it decides a move; a bare read is a snapshot.

A new thread takes its creator's set, or `KernelCpus.DefaultAffinity` when the creator is an idle thread, which is what the boot thread running `Main` is. The default is `KernelCpus.Compute`, every online CPU but CPU 0 (SMP phase 5, [#3343](https://github.com/CosmosOS/Cosmos/issues/3343)): the threads a kernel starts from `Main` run beside the boot CPU, not on it, and the scheduler spreads them over those CPUs. On one CPU `Compute` is that CPU, and on two it is CPU 1 alone. A kernel that wants its main flow everywhere sets `DefaultAffinity` to `KernelCpus.Online` before it creates threads, and one that wants every thread back on the boot CPU sets it to `KernelCpus.Housekeeping`.

`Environment.ProcessorCount` counts the default set, 3 on four CPUs, since those are the CPUs the thread pool's workers run on. CoreLib reads the count the first time something asks for it and keeps it, so a kernel that changes the default does it first thing in its startup, before a thread or the thread pool has asked. Changed later, the default still decides where new threads go, and the pool keeps the size it took.

The kernel's own service threads, every thread `KernelThread.TryStart` starts (the finalizer, the driver kit's threads, the console sessions', audio, the alarm thread), are housekeeping: CPU 0 whatever the default says. The split is a default rather than a partition: nothing keeps a thread off CPU 0 once its set names it, and `Compute` only names what is left of `Online` without it. It holds for the kernel's own threads for one reason: the driver stack excludes its interrupt handlers with interrupt masks, which is correct exactly as long as handler and thread share a CPU.

The effective set is the thread's set restricted to the CPUs online, or every online CPU when that leaves nothing, a kernel having pinned a thread to a CPU that is not up; the fallback is logged through the serial log once, when `SetAffinity` is handed such a set (a default set naming no online CPU is inherited without a line), as Linux does when every allowed CPU goes offline. The switch-out's hot check is `Affinity.Contains(cpu)` alone, and the online intersection runs only when that fails.

## The ring

A kernel reads and sets all of this through `Cosmos.Kernel.System.Threading`: `CpuSet`, the ring's projection of the seam's type with the same members, as `KernelThreadState` projects the seam's thread state; `KernelCpus` (`Count`, `Online`, `Housekeeping`, `Compute`, `Current`, which reads the per-CPU block and is exact on every CPU, and `DefaultAffinity`); and `ThreadAffinity` (`Current`, `TryGet` and `Set`, `TryGetIdealCpu` and `SetIdealCpu`, `Pin`). `KernelThreadInfo` carries `Affinity` and `IdealCpu`, so `SchedulerDiagnostics` shows them. The reads answer on every kernel: without a scheduler `Count` is 1 and `Online`, `DefaultAffinity` and `ThreadAffinity.Current` are `Housekeeping`. The writes need one: the `DefaultAffinity` setter and `ThreadAffinity.Set` throw `InvalidOperationException` when the scheduler is compiled out or not up, and `ArgumentException` for an empty set or one naming no CPU under `Count`; `Set`, `SetIdealCpu` and `Pin` return false for a thread the scheduler is not running and for an idle thread; `SetIdealCpu` throws `ArgumentException` for a CPU the thread's set excludes; and setting the calling thread's set throws `InvalidOperationException` from the boot thread, which runs `Main` on CPU 0's idle thread, and while interrupts are masked, because the move waits for the reschedule interrupt on that CPU. A `Thread` resolves to its control block through the handle the mechanism keeps: the calling thread always resolves, the boot thread included, and any other while the scheduler runs it.

A thread allocates on whichever CPU it runs, since the collector stops every CPU for a collection (SMP phase 4, [#3342](https://github.com/CosmosOS/Cosmos/issues/3342), [Stopping the world](../garbage-collector.md#stopping-the-world)), so none of these members is experimental.

## The mechanism

A set change on a thread no CPU is on, parked or queued, moves it at once through `SchedulerManager.MigrateThread`, the primitive of phase 3a: both queue locks in index order, `CpuId` rewritten, `OnThreadMigrate` for a queued thread so the policy rebases its virtual time, and the destination asked to reschedule by interrupt.

A thread a CPU is on cannot be moved from outside: it is left to that CPU's switch-out, which evicts a thread its CPU is excluded from. The thread is not re-queued, stays `Running` and out of every run structure, the CPU runs what the policy picked (its idle thread when the policy handed the evicted thread back), and once the queue lock is released, on the same interrupt exit, `MigratePending` asks `SelectCpu` for a destination inside the effective set, takes both locks and moves the thread (`OnThreadMigrate` sees it `Running` and in no structure), readies it there and sends the destination the reschedule interrupt.

A set change on a running thread asks its CPU to reschedule, by interrupt when it is another CPU's; a thread that excludes its own CPU raises the interrupt on it, as a park does, and returns from the setter on the new CPU.

What makes any resume on another CPU safe is the on-CPU marker. The handler that evicted or parked a thread runs on that thread's stack, and the thread's state says `Ready`, `Blocked` or `Sleeping` before the interrupt stub has left it, so the state cannot say whether a CPU is still on the thread. The switch-out stages the address of the outgoing thread's marker in the per-CPU block (`SwitchPrevOnCpu`) and the stub clears it right after it has switched stacks; the resuming CPU waits on the marker in `FinishSwitchFromIrq`, the last scheduler step of every interrupt exit, masked and under no lock, and then marks the thread its own. The wait is bounded by a stub that nothing holds up, and a marked thread enters another CPU's run structure only through the eviction its own CPU runs after its pick, so two CPUs never wait on each other. `MigrateThread` refuses a thread still marked, which hardens phase 3a's primitive too.

## Placement and balancing

Inside its set, where a thread runs is the policy's decision: it places a thread when it is created and each time it wakes, and it names a thread for a CPU that runs out of work to pull. The mechanism carries each decision out (SMP phase 5, [#3343](https://github.com/CosmosOS/Cosmos/issues/3343)).

`SelectCpu(thread, cpus, allowed)` is called wherever a thread needs a CPU: when it is created, which places its first start; at every wake of a parked thread no CPU is on; at a set change that excludes the thread's CPU; and at the eviction. A set of one CPU is answered without the hook. The wake is what spreads a running system: `ReadyThread` asks before it takes a queue lock, and when the answer is another CPU the parked thread moves there under both queue locks and is queued under the destination's. A thread whose CPU has not switched away from it yet is queued where it is.

`Balance(state, allCpuStates)` names a thread the policy wants pulled onto a CPU. The mechanism asks when that CPU's `PickNext` returned null, before it falls back on the idle thread, and on one tick in a hundred of every CPU, and it applies the answer when it still holds under both locks: the thread is still `Ready` on the CPU the policy named, that CPU's interrupt exit has left its stack, and its set allows the puller.

Stride's `SelectCpu` starts a woken thread from the CPU it is assigned to, the one it last ran on unless a set change moved it since, and any other placement from the ideal CPU, then the thread's CPU, then the set's first. From there it looks at the ideal CPU first and then at every other allowed CPU in index order, and moves on to each one whose load is under 80% of the best found so far. A woken thread therefore stays where its caches are unless another allowed CPU carries less than 80% of that CPU's load; two CPUs about as busy do not trade it back and forth. The load is `TotalTickets`, the tickets of the threads runnable on a CPU, its idle thread included, read under no lock. Its `Balance` answers only for a CPU whose queue is empty: among the CPUs whose queue holds at least two threads, it takes the longest queue that holds a thread allowed to move to the puller and names the one nearest its tail, walking each queue under its CPU's lock. Idle threads, threads whose set excludes the puller, threads their CPU has not left yet and threads queued for their first run do not count. Its `OnThreadMigrate` rebases a queued thread's `Pass` on the destination's `GlobalPass` plus the thread's `Remain`, computed from the source's clock for an evicted thread. A parked thread a wake places elsewhere needs no rebase: it parked with its `Remain` saved, and `OnThreadReady` computes its `Pass` from the `GlobalPass` of the CPU it wakes on, adding `Remain` unless the wake is interactive.

Timeouts follow the same path. Each CPU's tick wakes the sleepers assigned to it, so the timeout of a thread that went to sleep on CPU 2 is found by CPU 2's tick, and the wake goes through `SelectCpu` like any other.

The kernel's own threads stay on CPU 0 through all of this, with every device interrupt and the timers' callbacks. See [Limitations and evolution](../scheduler.md#limitations-and-evolution).
