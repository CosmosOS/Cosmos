# 内核启动

本文将介绍从上电到第一次调用你的内核的 `Run()` 方法之间发生的事情：启动链、各个初始化阶段，以及你的内核所依托的 `BeforeRun`/`Run`/`AfterRun` 生命周期。

如果你之前使用的是 Gen2，主要区别如下：

| | Gen2 | Gen3 |
|---|---|---|
| 编译器 | IL2CPU | .NET NativeAOT（ILC）+ Cosmos 的 IL patcher |
| 固件 | BIOS | UEFI，x64 和 ARM64 均如此 |
| 引导加载程序 | Limine | Limine |
| 入口衔接机制 | 由 IL2CPU 生成对 `Kernel.Start()` 的调用 | 由源代码生成器生成 `CosmosEntryPoint.Main()` |
| 生命周期 | `BeforeRun` / `Run` / `AfterRun` | `BeforeRun` / `Run` / `AfterRun`（未变） |

<a id="the-boot-chain"></a>

## 启动链

```
UEFI firmware
    │
Limine            loads kernel.elf, maps it in the higher half, sets up the framebuffer
    │
kmain()           native C bootstrap (Cosmos.Kernel/Bootstrap/kmain.c)
    ├─ Phase 1    CPU: enable SIMD, initialize the serial port
    ├─ Phase 2    Platform: RSDP + HHDM from Limine, early ACPI parse (MADT, MCFG)
    ├─ Phase 3    Managed runtime: heap, GC, type system, library initializers
    └─ Phase 4    User kernel: Main(argc, argv) → Kernel.Start()
```

[Limine](https://limine-bootloader.org/) 引导加载程序加载构建流水线生成的内核 ELF，然后跳转到 `kmain()`，这是一段编译进每个内核的小型 C 引导代码。从这里开始：

- **阶段 1：CPU。** 首先启用 SIMD（NativeAOT 生成的代码从第一条指令起就会使用 XMM 寄存器），并初始化串口，因此这一行之后的所有内容都会记录到日志中。在 ARM64 上，对齐检查也在这里被禁用。
- **阶段 2：平台。** 引导代码向 Limine 请求 ACPI RSDP 和高半区直接映射的偏移量，然后进行早期 ACPI 解析：MADT（中断控制器和 CPU 的描述所在）和 MCFG（PCIe 配置空间所在）。
- **阶段 3：托管运行时。** NativeAOT 的启动路径开始运行。C# 世界正是在这里一个包接一个包地运转起来（见下一节）。
- **阶段 4：用户内核。** 引导代码根据内核命令行构建 `argv`，并调用托管的 `Main`，最终进入你的内核的 `Start()`。

<a id="phase-3-how-the-managed-kernel-comes-up"></a>

## 阶段 3：托管内核如何启动

每个 Cosmos 包都会提供一个*库初始化器*（library initializer），运行时会在你的任何代码之前执行它。SDK 将它们分三个阶段排序：先是堆，然后是运行时自身的初始化器，最后是内核库，每个库都排在它所引用的包之后。

1. **Cosmos.Kernel.Core**：从 Limine 内存映射中划出堆，初始化垃圾回收器，然后注册类型系统（静态字段、立即执行的静态构造函数、模块初始化器）。在这一步之前，没有任何代码进行分配。
2. **运行时自身的初始化器**（`System.Private.CoreLib` 及其配套库）：预分配的 `OutOfMemoryException`、类构造函数运行器、类型加载器和反射回调、栈跟踪元数据。类构造函数运行器在这里创建，因此类型带有惰性静态构造函数的静态字段从这一步起才能读取，在此之前不行。
3. **Cosmos.Kernel.HAL**：平台 HAL；引导加载程序交出的设备树（如果有）会被记录下来（`[Firmware] Device tree at 0x..., N bytes`，在 q35 上以及以 ACPI 方式启动 virt 机器时则为 `[Firmware] No device tree`）；中断控制器、平台硬件（APIC/GIC、定时器），然后是机器的根平台节点，在 `InitializeHardware` 之后立即被发布到驱动工具包中（在 x64 上是 8042 键盘控制器 `platform:i8042@60`，然后是 PCI 主机 `platform:pci@cf8`；在 ARM64 上是来自 MCFG 或设备树的 ECAM 主机，以及每个已占用插槽对应的一个 `platform:virtio_mmio@...` 节点，这些节点来自设备树或 virt 机器的窗口，视开关的设置而定），它们在那里等待驱动阶段。8042、AHCI、NVMe 以及 USB 主机控制器（xHCI、EHCI、OHCI）不在这里启动：它们的驱动程序位于驱动工具包中，并在驱动阶段绑定它们。最后，只要启用了图形，无论是否启用中断，Limine 交出的帧缓冲区都会被记录下来（`[KERNEL]   - Recording the firmware framebuffer...`），供驱动阶段将其作为固件显示设备发布。
4. **Cosmos.Kernel**：CPU 异常处理程序和调度器（每个 CPU 一个空闲线程，以 10 ms 的时间片进行抢占）。
5. **Cosmos.Kernel.System**：服务管理器 `TimerManager`、`KeyboardManager`、`MouseManager`、`NetworkManager`、`DisplayManager`、`StorageManager`。`KeyboardManager`、`MouseManager`、`NetworkManager`、`DisplayManager` 和 `StorageManager` 都在这里、在驱动阶段之前安装各自的驱动工具包消费者，这样工具包驱动程序发布的键盘、指针、接口、显示设备或磁盘都会到达对应的管理器，驱动阶段最先发布的固件显示设备也是如此；这里不注册任何平台网络设备，工具包驱动程序发布的第一个接口会成为主接口。这里同样不注册任何平台键盘或鼠标：PS/2 设备与其他所有输入设备一样，在驱动阶段通过消费者到达。存储管理器的磁盘全部在驱动阶段通过它的消费者到达。

第 3 到 5 步中的每一步都受一个功能开关控制（`CosmosEnableInterrupts`、`CosmosEnablePCI`、`CosmosEnableTimer`、`CosmosEnableKeyboard`、`CosmosEnableMouse`、`CosmosEnableNetwork`、`CosmosEnableStorage`、`CosmosEnableGraphics`、`CosmosEnableScheduler`，默认均为 `true`；以及 `CosmosEnableUsb`，只要键盘、鼠标或存储开关中有一个开启，它默认就开启）。在你的 `.csproj` 中把其中一个设为 `false`，对应的子系统就会在这里被跳过，并从内核中被编译排除。

<a id="the-generated-entry-point"></a>

## 生成的入口点

你永远不需要为 Cosmos 内核编写 `Main`。SDK 自带一个源代码生成器，它会根据项目属性 `CosmosKernelClass` 生成这个方法：

```csharp
// <auto-generated/> CosmosEntryPoint.g.cs
namespace Cosmos.Kernel.System.Internal;

public static class CosmosEntryPoint
{
    public static void Main()
    {
        global::Cosmos.Kernel.System.Internal.DriverManifest.Register();
        global::Cosmos.Kernel.System.Internal.KernelEntry.Start(new global::MyOS.Kernel());
    }
}
```

`DriverManifest` 是第二个生成的文件：它是内核携带的驱动程序类列表，在内核启动之前注册，以便 `Start()` 中的驱动阶段能够向这些驱动程序提供设备。即使内核没有自己的驱动程序，也仍然携带 Cosmos 在 `Cosmos.Kernel.Drivers` 中提供的二十五个驱动程序：PCI 主机驱动、PCI Express 根端口驱动、Intel E1000E 驱动、virtio PCI 和 MMIO 传输驱动、virtio-net、virtio-input 和 virtio-blk 驱动、四个显示驱动（virtio-gpu、VMware SVGA II、AMD DCN 3.1.5 和 Intel 集成显卡）、两个存储驱动（AHCI 和 NVMe）、HD Audio 驱动、七个 USB 驱动（xHCI、EHCI 和 OHCI 主机控制器，以及集线器、HID 启动键盘、HID 启动鼠标和大容量存储类驱动），以及三个 PS/2 驱动（8042 控制器以及键盘和鼠标类驱动），其中二十二个受功能开关控制（七个 USB 驱动受 `CosmosEnableUsb` 控制，PS/2 键盘和鼠标受 `CosmosEnableKeyboard` 和 `CosmosEnableMouse` 控制，HD Audio 驱动受 `CosmosEnableAudio` 控制）。[驱动程序清单](../dev/build/driver-manifest.md)页面介绍了这份列表是如何构建的，以及项目如何排除或选择启用某个驱动程序。

`CosmosKernelClass` 默认为 `<RootNamespace>.Kernel`，因此项目根命名空间中名为 `Kernel` 的类会被自动选用。如果要使用其他类型，请显式设置该属性：

```xml
<PropertyGroup>
  <CosmosKernelClass>MyOS.Boot.MyKernel</CosmosKernelClass>
</PropertyGroup>
```

`KernelEntry.Start` 随后将该实例注册为 `Kernel.Current`，并调用它的 `Start()`。`KernelEntry` 是仅供这段生成代码使用的启动衔接代码，之所以是公共的，是因为这段代码会被编译进你的内核程序集；你自己的代码永远不会调用它。

## Sys.Kernel.Start()

`Cosmos.Kernel.System.Kernel` 是所有用户内核的抽象基类。它的 `Start()` 驱动整个生命周期：

1. 启用硬件中断（在此之前的一切都是在中断关闭的情况下运行的）。
2. 当 `CosmosEnableFinalizerThread` 开启时启动终结器线程，只要调度器开启，这个开关默认就是开启的：从这里开始，终结器在自己的线程上运行，而不是在执行回收或分配的那个线程上运行（[终结](../dev/garbage-collector.md#finalization)）。
3. 运行驱动阶段：工具包输出它的清单，将阶段 3 中记录的固件帧缓冲区作为固件显示设备发布（在某个显示驱动程序发布显示设备之前，它都是显示管理器的主显示设备），然后把总线已发布的每个节点提供给内核清单中列出的驱动程序：首先是阶段 3 中放入的平台节点（8042 驱动程序在探测过程中发布它的两个 PS/2 端口节点，键盘和鼠标驱动程序在该阶段中绑定它们），然后是 PCI 主机驱动程序找到的每个 PCI 功能，以及根端口驱动程序在其热插拔插槽后面找到的每个 PCI 功能，再然后是传输驱动程序在某个功能或插槽下发布的每个 virtio 设备，一旦每个节点（包括子节点）都已被提供，这一步就会返回；AHCI、NVMe、virtio-blk 和 USB 大容量存储驱动程序会在这里发布它们找到的磁盘（主机控制器驱动程序在探测过程中枚举其根端口，因此启动时已插入的 U 盘也会在该阶段中被发布），存储管理器在发布过程中注册并扫描每一个磁盘，因此当这一步返回时，`StorageManager.Partitions` 已经填好。每个 USB 主机控制器驱动程序的热插拔线程在其探测过程中启动，此后负责跟踪插入或拔出的设备；它需要调度器。根端口驱动程序的插槽线程对插入或拔出 PCI Express 热插拔插槽的设备做同样的事情，并为新到达的设备安排寄存器的位置；它同样需要调度器。
3. 调用 `OnBoot()`，其默认实现会在此时的主显示设备上初始化图形化的 `KernelConsole`，`Console.WriteLine` 正是因此才能工作。
5. 关闭早期启动阶段的文本渲染器：在此之前，你在屏幕上看到的启动日志是由一个极简的帧缓冲区写入器镜像输出的串口日志；从现在起，屏幕归 `Console` 和[画布](graphics.md)所有。
6. 调用一次 `BeforeRun()`。
7. 循环调用 `Run()`，直到 `Stop()` 被调用。
8. 调用一次 `AfterRun()`。
9. 让 CPU 停机。没有可以返回的操作系统：内核永远不会退出。

<a id="stopping-the-machine"></a>

## 停止机器

上面的第 9 步是内核自然到达的终点。`Power` 则让你主动到达那里，它的三个成员的区别在于做到哪一步：

```csharp
using Cosmos.Kernel.System;

Power.Halt();      // park this CPU until an interrupt wakes it
Power.Reboot();    // restart the machine; does not return
Power.Shutdown();  // power off; does not return
```

`Halt()` 是其中唯一会返回的成员。它让 CPU 停下等待，而不是空转，因此空闲循环应当调用它，而不是 `while (true) { }`；后者会占满一个核心，并且在单 CPU 内核上会让调度器无法推进。

`Reboot()` 和 `Shutdown()` 在成功时不会返回。两者都通过平台的电源操作完成，而在固件不提供任何电源操作时，它们会退而让 CPU 永远停下等待，而不是继续执行，这就是编译器将它们视为永不返回的原因。

如果要结束主循环而不关闭机器，请在你的内核上调用 `Stop()`。此后 `Run()` 不再被调用，`AfterRun()` 运行一次，然后 CPU 停机。

没有 `this` 可供调用的静态代码，可以通过 `Kernel.Current` 访问正在运行的实例；生成的入口点会在你的内核启动之前设置它（在此之前它为 `null`，在你的内核构造函数中也是如此）：

```csharp
using Cosmos.Kernel.System;

Kernel.Current?.Stop();
```

<a id="a-minimal-kernel"></a>

## 最小内核

```csharp
using System;
using Sys = Cosmos.Kernel.System;

namespace MyOS;

public class Kernel : Sys.Kernel
{
    protected override void BeforeRun()
    {
        Console.WriteLine("Cosmos booted successfully!");
    }

    protected override void Run()
    {
        Console.Write("Input: ");
        string? input = Console.ReadLine();
        Console.Write("Text typed: ");
        Console.WriteLine(input);
    }
}
```

- `BeforeRun()`：一次性的初始化工作（挂载[文件系统](filesystem.md)、配置[网络](network.md)、绘制启动画面）。
- `Run()`：主循环的循环体。它一返回就会被再次调用，因此它本身不需要循环；请保持它可重入。
- `Stop()`：可以在任何地方调用，用于在当前的 `Run()` 完成后退出循环。
- `AfterRun()`：循环结束后可选的清理工作。

`Run()` 中未捕获的异常会传播到循环之外，因此如果某条命令失败不应导致内核崩溃，请用 `try`/`catch` 包裹循环体。

<a id="customizing-startup"></a>

## 自定义启动过程

`OnBoot()` 在控制台存在之前运行，是进行你自己的早期初始化的合适位置。此时中断已经启用，驱动阶段也已运行，因此从这里开始，驱动程序已绑定的设备都可以使用；必须在中断关闭时运行的代码，应当放在对 `Start()` 本身的重写中：

```csharp
protected override void OnBoot()
{
    base.OnBoot();   // keep the KernelConsole setup; drop this line to boot headless

    // your early initialization here
}
```

之后需要 `Console` 输出的无头（headless）内核要自己调用 `KernelConsole.Initialize()`：这是受支持层上唯一的途径，`Console.WriteLine` 不会自行启动控制台。这个调用是幂等的，因此无论 `base.OnBoot()` 是否已经运行，调用它都是安全的；当图形被编译排除、没有发布任何显示设备，或者显示设备没有任何模式时，它返回 `false`。

如果需要完全的控制，你可以重写 `Start()` 本身并接管生命周期：[`Cosmos.Kernel.System/Kernel.cs`](https://github.com/CosmosOS/Cosmos/blob/gen3/src/Cosmos.Kernel.System/Kernel.cs) 中的默认实现很短，是一个很好的复制起点。

<a id="the-kernel-command-line"></a>

## 内核命令行

Limine 会向内核传递一条命令行，即内核项目中 `Bootloader/limine.conf` 文件的 `cmdline:` 条目。通过标准方式即可获取它：

```csharp
foreach (string arg in Environment.GetCommandLineArgs())
{
    Console.WriteLine(arg);
}
```

<a id="summary"></a>

## 总结

| 任务 | 调用 |
|---|---|
| 在主循环之前进行一次性初始化 | `BeforeRun()` |
| 编写主循环的循环体 | `Run()` |
| 循环结束后进行清理 | `AfterRun()` |
| 让 CPU 停下等待中断 | `Power.Halt()` |
| 重启机器 | `Power.Reboot()` |
| 关闭机器电源 | `Power.Shutdown()` |
| 结束主循环 | `Stop()` |
| 从静态代码访问正在运行的内核 | `Kernel.Current` |
| 在控制台存在之前进行早期初始化 | `OnBoot()` |
| 在无头内核上启动控制台 | `KernelConsole.Initialize()` |
| 接管整个生命周期 | `Start()` |
| 读取内核命令行 | `Environment.GetCommandLineArgs()` |
