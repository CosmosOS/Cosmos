# 物理地址

在启用了分页的 CPU 上运行的代码从不直接指明内存。它持有的每个指针都是虚拟地址，内存管理单元通过页表把它转换成物理地址，也就是内存总线实际传送的位置，位于 RAM 中或设备的寄存器空间中。转换以页为单位进行，通常每次 4 KiB，相邻的虚拟页不一定映射到相邻的物理页。

设备位于这一转换之外。设备通过 [DMA](dma.md) 读写内存时，会把地址直接放到总线上，没有页表可查，因此驱动程序交给它的是缓冲区的物理地址，绝不是驱动程序自身代码使用的指针。IOMMU 可以为设备提供它们自己的地址转换；没有 IOMMU 时，设备地址就是物理地址。这种分离在反方向上同样存在：设备的[寄存器](registers.md)位于某个物理地址上，内核要先把它映射到虚拟地址空间，CPU 才能访问。

由此产生两个约束。在虚拟内存中连续的缓冲区可能分散在多个物理页上，而被要求从某个地址传输 N 字节的设备，读取的是物理上连续的 N 个字节，因此驱动程序要么分配物理连续的内存，要么把分散的缓冲区描述为一个片段列表。设备还有对齐要求：保存基址的寄存器常常忽略其低位，有些结构不能跨越页边界。

陷阱在于这两种地址都只是普通整数。没有任何机制阻止驱动程序把虚拟地址交给设备，而设备随后会读写一个毫不相干的物理位置，也没有任何故障能指出问题出在哪里。

在驱动工具包中，由 `binding.AllocateDma(length, alignment)` 得到的 `DmaBuffer` 同时提供这两种视图：它是物理连续的，起始地址至少按 4 KiB 边界对齐，并带有供 CPU 使用的 `Span` 和供设备使用的 `PhysicalAddress`。节点的内存窗口（`DeviceResource.PhysicalBase`，以及内存 BAR 的 `PciBar.Base`）都是物理地址，由 `MapRegisters` 和 `MapRegion` 使其可以访问；内核不设置任何 IOMMU，所以设备使用的就是物理地址。参见 [DMA 内存](../drivers.md#dma-memory)和 [BAR 资源](../drivers.md#bar-resources)。
