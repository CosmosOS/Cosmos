# 固件交接

内核并不是机器上第一个运行的软件。UEFI 固件在引导加载程序之前运行，等到它交出控制权时，它已经为自身用途配置好了很大一部分硬件。它已经枚举了 PCI，为各个桥分配了总线号，为每个功能的 BAR 分配了地址（[PCI](pci.md)），并启用了它从中启动的设备。它通过自己的 Graphics Output Protocol（图形输出协议）设置了显示模式，并在屏幕上留下一个线性帧缓冲区，引导加载程序会把这个帧缓冲区的地址、大小和像素布局传给内核。描述那些无法被发现的内容的表也以同样的方式到达内核：在 PC 和 ARM 服务器上是 ACPI，在许多 ARM 开发板上是设备树（[总线](buses.md)）。

内核可以重做这些工作，也可以在此基础上继续。沿用固件的成果可以省去工作，尤其是显示模式：设置模式意味着编程显示时序并建立与显示器之间的链路，而这些固件已经做过了。代价是内核会继承可能仍处于活动状态的设备：总线主控仍开启、DMA 仍在进行，或者固件仍在用某个 USB 控制器模拟 PS/2 键盘。

陷阱在于传统启动。借助 CSM（兼容性支持模块），UEFI 固件会模拟老式 PC BIOS，显示停留在 VGA 模式，而不是线性帧缓冲区上，因此期望使用固件表面的驱动程序将找不到任何表面。

在驱动工具包中，PCI 主机驱动程序沿用固件留下的配置：它保留固件分配的总线号和 BAR，而不是重新分配。工具包会在第一次探测之前关闭功能的总线主控和中断，这样任何驱动程序都不会看到固件留下仍在运行的设备；当没有驱动程序绑定该功能时，工具包会恢复固件的设置（[PCI 访问对象](../drivers.md#the-pci-access-object)）。引导加载程序的帧缓冲区被发布为名为 `framebuffer` 的显示设备，当某个驱动程序绑定了其内存中包含该帧缓冲区的 PCI 功能时，它会被撤回（[发布设备](../drivers.md#publishing-a-device)）。`AmdDcnDriver` 和 `IntelGraphicsDriver` 保留 UEFI 模式，在 CSM 启动之后拒绝绑定，并在 `OnDetach` 中把固件的表面重新显示到屏幕上（[显示设备驱动程序](../drivers.md#the-display-drivers)）。
