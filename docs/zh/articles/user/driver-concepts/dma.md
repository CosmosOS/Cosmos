# DMA（直接内存访问）

使用程序控制 I/O 时，CPU 要亲自通过设备寄存器复制每一个字，面对高速网卡或磁盘，这会让一个核心一直忙于此事。使用直接内存访问时，设备自行读写主内存：驱动程序把一个缓冲区的[物理地址](physical-addresses.md)和长度交给设备（通常通过[描述符环](descriptor-rings.md)），设备在 CPU 处理其他工作的同时搬运数据，然后报告传输完成，报告方式通常是中断。

自行发起内存事务的设备称为总线主控设备（bus master）。在 [PCI](pci.md) 上，一个功能只有在其命令寄存器的 Bus Master Enable 位被置位时才能这样做，这让操作系统能够让它停下。有些设备只驱动 32 位地址，只能访问物理内存的前 4 GiB。

CPU 会缓存内存，而在缓存背后工作的设备可能读到过时的数据，或者留下过时的缓存行。在一致性平台上（x64 PC 就属于这种平台），硬件会让设备的访问与缓存保持一致；在非一致性平台上，驱动程序要在每次传输前后清理缓存行或使其失效。不过，一致性并不规定任何顺序，因此驱动程序在写入数据和告诉设备数据已就绪之间仍然需要[屏障](barriers.md)。

陷阱在于 DMA 绕过了内核用来保护内存的一切手段。设备会一直向交给它的地址写入，直到被停下为止，因此在传输进行期间被释放的缓冲区，会在重新使用这块内存的任何对象内部被覆盖。垃圾回收器又增加了一种让缓冲区被意外释放的途径：一旦某个对象不再有任何引用，它就会回收该对象，而描述符中的地址并不是它能看到的引用。

在驱动工具包中，由 `binding.AllocateDma` 得到的 `DmaBuffer` 会一直存在，直到拆除过程在 `OnDetach` 之后将其释放，因此驱动程序只把这样的缓冲区交给设备，绝不交出托管数组。带 `DmaConstraints.Addressable32Bit` 调用 `TryAllocateDma` 时，如果缓冲区的末尾会超过 4 GiB，它就返回 `false`：工具包没有低端内存池，所以它照常分配，再把这样的缓冲区归还。工具包在 x64 和 ARM64 上都把 DMA 视为一致的。它在第一次探测之前关闭 PCI 功能的总线主控，并在每次未能完成绑定的探测之后、该探测的缓冲区被释放之前再次关闭，这样每次探测都从一个无法写入内存的功能开始，而被拒绝的探测所对应的设备也会在其缓冲区归还之前停下；驱动程序用 `PciAccess.EnableBusMastering(true)` 重新打开它。参见 [DMA 内存](../drivers.md#dma-memory)和 [PCI 访问对象](../drivers.md#the-pci-access-object)。
