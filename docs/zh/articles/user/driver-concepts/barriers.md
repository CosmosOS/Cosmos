# 内存屏障

程序的加载（load）和存储（store）不一定按源代码列出的顺序到达内存。编译器可能重排它认为彼此独立的访问，CPU 也可能让较晚的存储先于较早的存储变得可见，或者让较晚的加载先于较早的加载执行，只要正在运行的线程察觉不到即可。设备却能察觉：它自行读写 [DMA](dma.md) 内存，只能看到 CPU 的存储变得可见的顺序。

交出一个[描述符](descriptor-rings.md)就能说明这个问题。驱动程序先填好地址和长度，再设置把描述符交给设备的标志；如果标志先变得可见，设备就会按旧的长度工作。完成则是与之对称的情形：驱动程序读取设备设置的标志，再读取该标志表明已就绪的数据，而提前加载了数据的 CPU 返回的是设备写入之前的内容。在描述符和标志之间放一道写屏障，可以让之前的每次存储都先于之后的任何存储变得可见。在标志和数据之间放一道读屏障，可以防止之后的加载跑到它前面。两者还都会阻止编译器把访问移到屏障的另一侧。

陷阱在于，x64 自身就会保持存储与存储之间、加载与加载之间的顺序，所以缺少屏障在那里不会造成任何危害。问题会在 ARM64 上暴露出来，它的内存模型允许这两类访问都被重排，因此只在 x64 上测试过的驱动程序可能长期带着这个 bug。

在驱动工具包中，`DmaBuffer.WriteBarrier()` 和 `DmaBuffer.ReadBarrier()` 就是这两种屏障：在 ARM64 上是真正的栅栏（fence）指令，在 x64 上不生成任何指令，但仍会阻止编译器把访问移到它们的另一侧。每次 `RegisterWindow` 写入之前都有一道写屏障，每次读取之后都有一道读屏障，因此填好描述符之后的门铃写入不需要自己的屏障；而 `DeviceRegion` 不带任何屏障，由驱动程序自己放置。参见 [DMA 内存](../drivers.md#dma-memory)和[寄存器窗口](../drivers.md#register-windows)。
