<a id="driver-manifest"></a>

# 驱动程序清单

每个 Cosmos 内核都会从 `Cosmos.Kernel.SourceGenerators` 得到两个生成的文件：入口点和驱动程序清单。本页介绍这份清单：两个生成器分别写出什么，构建会注册哪些 `[Driver]` 类、按什么顺序注册，功能开关如何为一次注册加上守卫，内核项目如何排除某个驱动程序或显式启用某个驱动程序，以及生成器无法满足某个类的要求时会报告什么；页末介绍其背后的构建底层机制、可见性规则和测试。关于清单在启动序列中的运行时机，请参阅[内核启动](../../user/startup.md)。

清单之所以存在，是因为没有其他办法能找到驱动程序。内核是预先编译的，内核代码不使用反射，因此内核启动时无法在自己的程序集中搜索驱动程序类，而[裁剪（trimming）](../../user/driver-concepts/trimming.md)会把任何没有被代码引用的类排除在镜像之外。清单就是引用每个驱动程序的那段代码：[源代码生成器](../../user/driver-concepts/source-generators.md)在构建时根据它找到的 `[Driver]` 类和项目的策略写出清单，清单没有构造的驱动程序就不会出现在内核中。清单的顺序同样重要，当驱动工具包为一个设备[在多个驱动程序之间做选择](../../user/driver-concepts/driver-matching.md)时，它是最后一个判定依据。这些概念以及驱动程序所依赖的硬件概念，在[驱动程序术语表](../../user/driver-glossary.md)中有背景说明，[编写驱动程序](../../user/drivers.md)则从驱动程序作者的角度介绍驱动工具包。

<a id="what-is-generated"></a>

## 生成的内容

每个文件都有自己的生成器。`CosmosEntryPointGenerator` 仅根据 `CosmosKernelClass` 属性写出入口点，因此修改内核的源代码或其驱动程序策略时，入口点仍保持缓存；`DriverManifestGenerator` 则根据它找到的驱动程序和策略写出清单。该属性为空时，两个文件都不会生成。属性已设置时，入口点总是先调用清单。这个调用是显式的，而不是模块初始化器，因此驱动程序会按清单顺序注册，紧接在内核启动之前。下面展示的两个文件都省略了文档注释和 `[GeneratedCode]` 特性：

```csharp
// <auto-generated/> CosmosEntryPoint.g.cs
namespace Cosmos.Kernel.System.Internal;

public static class CosmosEntryPoint
{
    public static void Main()
    {
        global::Cosmos.Kernel.System.Internal.DriverManifest.Register();
        global::Cosmos.Kernel.System.Internal.KernelEntry.Start(new global::MyOS.Kernel());
    }
}
```

```csharp
// <auto-generated/> DriverManifest.g.cs
// The driver registry is on the experimental driver kit seam (COSMOS0003).
// This file is generated, so it acknowledges the seam for itself alone;
// a driver this kernel declares still meets the diagnostic in its own code.
#pragma warning disable COSMOS0003
namespace Cosmos.Kernel.System.Internal;

internal static class DriverManifest
{
    public static void Register()
    {
        global::Cosmos.Kernel.HAL.DriverKit.DriverRegistry.Register(new global::MyOS.Drivers.BoardDriver());
        if (global::Cosmos.Kernel.System.KernelFeatures.Network)
        {
            global::Cosmos.Kernel.HAL.DriverKit.DriverRegistry.Register(new global::Acme.Drivers.AcmeNicDriver());
        }
    }
}
```

清单中每个驱动程序对应一个 `Register` 调用，每个调用都用驱动程序的无参构造函数构造它。即使没有任何驱动程序保留下来，清单也照样生成，此时 `Register` 的方法体为空。清单调用的注册表位于驱动工具包的实验性扩展点上，而 Cosmos 自带的驱动程序会在每个内核的清单中放入调用，因此该文件开头只为自身禁用这个扩展点的诊断 ID：这个文件不是内核作者写的，而且没有抑制该 ID 的内核（参见[可见性](#visibility)）也仍然能够编译。

启用 `EmitCompilerGeneratedFiles` 时（`Cosmos.Sdk` 默认启用它），两个文件都会写到中间目录下，每个生成器一个文件夹：

```
$(IntermediateOutputPath)/generated/Cosmos.Kernel.SourceGenerators/
    Cosmos.Kernel.SourceGenerators.CosmosEntryPointGenerator/CosmosEntryPoint.g.cs
    Cosmos.Kernel.SourceGenerators.DriverManifestGenerator/DriverManifest.g.cs
```

在那里阅读 `DriverManifest.g.cs`，是检查一个内核带有哪些驱动程序的最快方式。

<a id="how-drivers-are-found"></a>

## 如何找到驱动程序

驱动程序是标记了 `[Cosmos.Kernel.HAL.DriverKit.Driver]` 的类。生成器在两个地方查找，并保持两者的顺序固定，因为当两个优先级和特异性都相同的驱动程序匹配同一个设备时，清单中的位置是最后一个仲裁依据（[驱动程序匹配](../../user/driver-concepts/driver-matching.md)）：

| 来源 | 哪些类 | 顺序 |
|--------|---------------|-------|
| 内核项目本身 | 该程序集能从其顶层构造的每个标记类（私有嵌套类会以 `COSMOSGEN001` 报告并被排除） | 先按文件路径（序数比较），再按在文件中的位置 |
| 引用了 `Cosmos.Kernel.HAL`（或本身就是它）的被引用程序集 | 内核程序集能看到的标记类：公共类，以及在 `InternalsVisibleTo` 授权下的内部类 | 先按程序集名称，再按完整类型名称，两者都按序数比较 |

内核自己的驱动程序排在前面，然后是被引用程序集中的驱动程序。不引用 `Cosmos.Kernel.HAL` 的程序集不会被搜索，因为它不可能带有该特性。

要被注册，一个类必须是具体的（既不是抽象类，也不是静态类）且非泛型，派生自 `Cosmos.Kernel.HAL.DriverKit.Driver`，并且具有内核程序集可以调用的无参构造函数。不满足其中任何一条的标记类会被报告（`COSMOSGEN001`）并被排除。

Cosmos 自带的驱动程序走的是第二条路径。它们位于 `Cosmos.Kernel.Drivers` 中，每个内核都引用的聚合包 `Cosmos.Kernel` 带有这个程序集，因此全部二十五个驱动程序都会出现在每个内核的清单中，排在内核自己的驱动程序之后，而内核本身无需引用该包。它们按完整类型名称排序，而自带驱动程序的完整名称包含其总线种类、类别和驱动程序文件夹（`Cosmos.Kernel.Drivers.Pci.Storage.Nvme.NvmeDriver`），因此这个顺序会按总线种类（`Pci`、`Platform`、`Ps2`、`Usb`、`Virtio`）对它们分组，同一总线种类内再按类别分组。其中二十二个在功能守卫下注册，三个没有任何守卫：

| 功能 | 驱动程序 |
|---------|---------|
| `Pci` | `PciHostDriver`, `PcieRootPortDriver`, `VirtioPciTransportDriver` |
| `Network` | `E1000EDriver`, `VirtioNetDriver` |
| `Graphics` | `VirtioGpuDriver`, `VmwareSvgaDriver`, `AmdDcnDriver`, `IntelGraphicsDriver` |
| `Storage` | `AhciDriver`, `NvmeDriver`, `VirtioBlkDriver` |
| `Audio` | `HdAudioDriver` |
| `Usb` | `XhciDriver`, `EhciDriver`, `OhciDriver`, `UsbHubDriver`, `UsbKeyboardDriver`, `UsbMouseDriver`, `UsbMassStorageDriver` |
| `Keyboard` | `Ps2KeyboardDriver` |
| `Mouse` | `Ps2MouseDriver` |
| 无 | `VirtioMmioTransportDriver`, `VirtioInputDriver`, `I8042Driver` |

<a id="feature-guards"></a>

## 功能守卫

`[Driver(Feature = DriverFeature.Network)]` 把注册与一个[功能开关](../../user/driver-concepts/trimming.md)关联起来。生成器把 `Register` 调用包在一个 `if` 中，条件是 `Cosmos.Kernel.System.KernelFeatures` 上的同名属性，每个 `if` 只有一个属性，条件中没有其他内容，这正是 [ILC](ilc-build.md) 会折叠为常量的形式。于是，把 `CosmosEnableNetwork` 设为 `false` 的内核永远不会构造该驱动程序；而且由于没有其他代码会构造自带的驱动程序，所有只被该驱动程序引用的内容都会随它一起被裁剪掉。

`DriverFeature` 枚举的成员按名称与 `KernelFeatures` 的属性一一对应（`Interrupts`、`Uart`、`Pci`、`Timer`、`Keyboard`、`Mouse`、`Network`、`Storage`、`Fat`、`Graphics`、`Scheduler`、`Usb`、`Audio`），`None` 则不生成守卫。生成器在内核的编译中解析该属性，因此没有对应属性的成员会成为构建错误（`COSMOSGEN003`），而不是生成一份无法编译的清单。`tests/Cosmos.Tests.SourceGenerators` 中的 `FeatureParityTests` 让这两份列表保持同步。

<a id="excluding-and-opting-in"></a>

## 排除与显式启用

内核项目用两种项类型决定它的清单，也就是它的驱动程序策略：

```xml
<ItemGroup>
  <!-- Drop a driver the build would otherwise register. -->
  <CosmosDriverExclude Include="Acme.Drivers.AcmeNicDriver" />
  <!-- Register a driver declared [Driver(Default = false)]. -->
  <CosmosDriverInclude Include="Acme.Drivers.ExperimentalGpu" />
</ItemGroup>
```

名称是 C# 形式的完整类型名称，不带 `global::`，嵌套类型用点连接（`MyOS.Drivers.Bus.Child`）。自带的驱动程序也用同样的方式排除，即使用其完整类型名称：`<CosmosDriverExclude Include="Cosmos.Kernel.Drivers.Pci.Network.E1000E.E1000EDriver" />` 会让 Intel 驱动程序不进入清单。

被排除的驱动程序无论其 `Default` 为何值都会被丢弃，而 `Default = false` 的驱动程序只有在某个 `CosmosDriverInclude` 项指名它时才会注册。不匹配内核可见的任何 `[Driver]` 类的项会被报告（`COSMOSGEN002`），过时或拼错的条目就是这样暴露出来的。策略在验证之前应用，因此内核排除的或没有显式启用的驱动程序永远不会被报告，下文的诊断针对的是清单将会注册的内容。

<a id="diagnostics"></a>

## 诊断

生成器报告三种诊断，全部属于 `Cosmos.DriverKit` 类别：

| ID | 严重性 | 含义 |
|----|----------|---------|
| `COSMOSGEN001` | 警告 | 某个 `[Driver]` 类被排除：它是抽象类、静态类或泛型类，不派生自 `Driver`，没有内核程序集可以调用的无参构造函数，或者无法从内核程序集访问。消息会说明具体原因。 |
| `COSMOSGEN002` | 警告 | 某个 `CosmosDriverExclude` 或 `CosmosDriverInclude` 项不匹配内核可见的任何 `[Driver]` 类。 |
| `COSMOSGEN003` | 错误 | 某个 `[Driver]` 指定的 `DriverFeature` 成员没有同名的 `KernelFeatures` 属性，因此无法为该注册加上守卫。 |

这些规则列在 `src/Cosmos.Kernel.SourceGenerators/AnalyzerReleases.Unshipped.md` 中，这是 Roslyn 分析器包所要求的版本跟踪格式。

<a id="build-plumbing"></a>

## 构建底层机制

生成器只读取项目向它公开的构建属性（[源代码生成器](../../user/driver-concepts/source-generators.md)）。这两个生成器读取三个属性，它们由 `Cosmos.Kernel.SourceGenerators.props` 中的 `CompilerVisibleProperty` 项公开，该文件随生成器包一起分发。入口点生成器只读取 `CosmosKernelClass`，清单生成器则读取全部三个：

| 属性 | 设置者 | 读取方式 |
|----------|--------|---------|
| `CosmosKernelClass` | 内核项目，或由 `Sdk.props` 根据 `RootNamespace` 设置 | `build_property.CosmosKernelClass` |
| `CosmosDriverExcludeList` | `Sdk.targets` 中的 `CosmosCollectDriverPolicy` 目标，它把各个 `CosmosDriverExclude` 项连接起来 | `build_property.CosmosDriverExcludeList` |
| `CosmosDriverIncludeList` | 同一个目标，它把各个 `CosmosDriverInclude` 项连接起来 | `build_property.CosmosDriverIncludeList` |

这个目标有两个细节，修改它的人需要注意。这些项是在目标内部连接的，而不是在求值阶段的 `PropertyGroup` 中，因为项引用在那里不会展开；并且该目标以 `BeforeTargets="GenerateMSBuildEditorConfigFileCore"` 运行，也就是在写出编译器 editorconfig 的那一步之前。分隔符是逗号，因为编译器把该文件当作 editorconfig 读取，而在 editorconfig 中分号表示注释的开始，所以用分号连接的列表会在第一个名称之后被截断。

<a id="visibility"></a>

## 可见性

驱动工具包是公开的，但处在实验性扩展点 `COSMOS0003` 之下：`Driver`、`DriverAttribute`、`DriverRegistry` 以及 `Cosmos.Kernel.HAL.DriverKit` 下的其他所有类型都带有 `[Experimental("COSMOS0003")]`。因此，声明了 `[Driver]` 类的内核或库要在其 `.csproj` 中抑制这个 ID，驱动程序库还要把自己声明为驱动程序程序集：

```xml
<PropertyGroup>
  <NoWarn>$(NoWarn);COSMOS0003</NoWarn>
  <!-- A class library of drivers only: held to the public surface by the analyzer. -->
  <CosmosDriverAssembly>true</CosmosDriverAssembly>
</PropertyGroup>
```

不声明自己驱动程序的内核不需要抑制。生成的清单会为自身禁用该 ID，因为它不是内核作者写的，而且它是这类内核唯一提到驱动工具包的地方；抑制针对的是内核或库所声明的驱动程序代码。[编写驱动程序](../../user/drivers.md)从驱动程序作者的角度介绍驱动工具包和项目文件中的相关配置行，[公共 API 跟踪](../public-api.md)则介绍驱动程序程序集需要遵守的约束。

<a id="testing"></a>

## 测试

`tests/Cosmos.Tests.SourceGenerators` 在主机上针对内存中的编译运行这两个生成器，用桩代码代替驱动工具包和受支持层，并逐字检查生成的文本和诊断。`CachingTests` 检查添加驱动程序会重新生成清单，同时入口点保持缓存。这个套件可以用以下命令单独运行：

```bash
dotnet test tests/Cosmos.Tests.SourceGenerators -c Debug
```

CI 将它作为 `.github/workflows/dotnet.yml` 中的 `source-generator-tests` 作业运行。
