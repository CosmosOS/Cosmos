# 上下文切换

上下文切换让一个 CPU 从一个线程转到另一个线程。换出线程的寄存器被保存在内核之后还能找到的地方，通常是该线程自己的栈上或它的控制块中；栈指针被指向换入线程已保存的状态，再恢复它的寄存器，于是它恰好从停下的地方继续执行。内核通过两种途径进入切换。被动切换发生在中断时：中断入口已经保存了被中断线程的寄存器，所以内核只需返回到另一个已保存的状态中。主动切换发生在线程调用内核以阻塞或让出时，经由一个自己保存寄存器的例程完成。

一次切换的代价不止于它复制的那些寄存器。换入线程会发现缓存和地址转换缓冲区里装满了另一个线程的数据，在把它们重新预热之前都会运行得更慢，这就是调度器的切换频率不会超出其策略所需的原因。

陷阱在于，决定切换与执行切换是两个独立的步骤。调度器可以在某个节拍中，或在某个线程被唤醒时作出决定，而切换本身只在内核离开中断时才发生。决定与切换之间的一切都必须与该决定保持一致：被记录为当前线程的线程、被放回队列的线程，以及 CPU 将要恢复的栈，必须全都描述同一次切换，否则 CPU 恢复运行的线程，在簿记中却位于别处。

在 Cosmos 中，每次切换都发生在中断退出时。中断桩代码把线程的寄存器（包括 SIMD 状态）保存在该线程的栈上；管理器调用 `PickNext`，在旧线程的 `SchedulerThread.StackPointer` 中记录其状态所在的位置，并暂存新线程的状态，桩代码在退出途中据此恢复。线程的首次运行没有可供返回的已保存帧，因此改为跳转到它的入口点。任何中断的退出都可能带来一次切换：定时器节拍在 `OnTick` 返回 `true` 时如此；任何硬件中断，只要唤醒、阻塞、`Thread.Yield` 或策略替换已经请求了重新调度，也是如此，此时无论 `OnTick` 回答了什么，`PickNext` 都会运行，而当该中断不是节拍时，则根本不经过 `OnTick`。不存在主动切换：阻塞的线程在自己的 CPU 上触发一个中断来切换出去（空闲线程则改为停机），而 `Thread.Yield` 会立即返回，把切换留给下一次中断退出。策略从不接触寄存器。参见[节拍](../scheduler.md#the-tick)和[不存在的东西：主动切换](../scheduler.md#what-there-is-not-a-voluntary-switch)。
