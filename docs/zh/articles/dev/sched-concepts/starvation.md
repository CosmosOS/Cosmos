# 饥饿与老化

线程已经就绪、可以运行，调度器却始终不选中它，这就是饥饿（starvation）。严格优先级很容易导致这种情况：只要有任何更高优先级的线程就绪，较低优先级的线程就不会运行，而一个繁忙的高优先级等级可以无限期地把它挡在 CPU 之外。对线程分等级的调度器用老化（aging）来保护低等级：线程等待得越久，它的优先级就被提得越高；或者用周期性提升：每隔一段时间把所有线程拉回最高等级。[公平份额](virtual-time-fair-share.md)调度器从构造上就避免了饥饿，因为每个权重为正的线程都会得到自己的份额，但被唤醒线程的放置方式可能让饥饿重新出现：一个在虚拟时间上被放置得远远落后于其他线程的线程会先运行，直到追上它们为止，在此期间它一直占着 CPU，其他所有线程都得不到运行。

陷阱在于，饥饿通常是一个簿记错误，而不是策略本身的性质。一个离开了运行队列却再也没有被放回的线程、一个把同一线程保存了两次的队列，以及一个顺序已被破坏的有序队列，从外部看都一样：某个线程不再运行，而策略中没有任何一条规则说它应该如此。当一个线程在一个本不应让任何线程饥饿的策略下陷入饥饿时，首先要检查的是每个就绪线程是否恰好入队一次。

在 Cosmos 中，Stride 策略的 `OnThreadYield` 会在线程落后时把它的 `Pass` 提升到该 CPU 的 `GlobalPass`，因此一个很早就启动的线程（例如空闲线程）无法一直排在后来创建的线程前面。唤醒放置也以同样的方式设防，分两步进行。被唤醒的线程不是以它离开时的 `Pass` 重新入队，而是以 `GlobalPass` 加 `Remain` 重新入队，`Remain` 是它挂起时的偏移量：`Remain` 在挂起时就被冻结，因此睡得更久并不会让它变小，长时间的睡眠也就换不来排在所有其他线程前面的长时间运行。上限（落后 `GlobalPass` 绝不超过两个 `Stride1`）约束的是线程挂起时就已经是很大负值的 `Remain`，而线程离开 CPU 时施加的下限让这种情况很少出现。管理器则在自己这一侧维护只入队一次的规则。对已经是 `Ready` 或 `Running` 的线程进行唤醒不起任何作用，而一次切换只有在离开 CPU 的线程仍为 `Running` 时才把它放回队列，因为在 Stride 的有序队列中，第二个条目会在线程的 `Pass` 上升时保持原位，而只取队首的 `PickNext` 将永远到达不了排在它后面的线程。对线程分等级的策略会自带防护：MLFQ 示意实现每隔几个节拍就把所有线程重置到最高等级。参见 [Stride 策略](../scheduler.md#the-stride-policy)和[示意实现](../../user/scheduler-plugging.md#worked-sketches)。
