# 自旋锁与中断屏蔽

自旋锁保护数据不受另一个 CPU 上运行的代码干扰：发现锁已被占用的线程会循环等待，直到持有者将其释放。这之所以可行，是因为在另一个 CPU 自旋时，持有者仍在自己的 CPU 上继续运行。但面对同一个 CPU 上的中断处理程序，这一点就不成立了。如果处理程序在被它中断的代码持有锁时触发，并且自己也试图获取这个锁，它就会自旋，而持有者在处理程序返回之前无法释放锁，于是这个 CPU 会永远自旋下去。

因此，与中断处理程序共享数据的代码会在每次访问期间屏蔽其所在 CPU 上的中断，使处理程序无法在访问中途触发。对于 CPU 自己的中断，屏蔽是它唯一需要的保护，但面对其他 CPU 仍然需要自旋锁，所以内核把两者结合成一种中断安全锁：先屏蔽，再获取锁；先释放锁，再恢复。屏蔽会保存先前的中断状态并在之后恢复它，而不是直接重新开启中断，因此一个被屏蔽的区段可以嵌套在另一个之中。

陷阱在于不获取任何锁的代码。锁只能排斥获取同一把锁的代码，而一个中断处理程序如果不获取该锁就访问数据（这往往是因为它不允许等待），线程一侧持有的任何锁都无法把它挡在外面。只有屏蔽才能挡住这样的处理程序。此外，屏蔽恰好只让一个区段具有原子性：先在一次屏蔽调用中读取数量、再在后续调用中遍历各个元素的调用者，可能会看到结构在这些调用之间发生变化。

在 Cosmos 调度器中，节拍路径完全不获取任何锁：`OnTick` 在定时器中断内部运行，`PickNext` 在执行重新调度的那次中断退出内部运行，两者都依赖于中断在那里已被屏蔽。管理器在调用线程生命周期钩子和两个每 CPU 钩子时会屏蔽中断，因此节拍不可能落在它们内部。`SchedulerManager.SetPriority` 持有一个不屏蔽中断就获取的每 CPU 自旋锁，它能挡住第二个调用者，却挡不住节拍；而 `GetPriority`、`GetRunQueueCount` 和 `GetRunQueueThread` 被调用时完全没有任何保护。这四个钩子，以及策略自己添加的任何入口点，都通过 `SchedulerManager.MaskInterrupts()` 屏蔽中断，其 `InterruptMaskScope` 在被释放时会恢复先前的状态，因此在已经屏蔽中断的钩子内部再次屏蔽不会造成任何问题。参见 [SpinLock 与 IRQ 安全作用域](../scheduler.md#spinlock-and-the-irq-safe-scope)和[内核约束](../../user/scheduler-plugging.md#kernel-constraints)。
