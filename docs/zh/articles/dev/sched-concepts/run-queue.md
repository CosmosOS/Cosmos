# 线程状态与运行队列

在任一时刻，线程都处于少数几种状态之一。CPU 执行它时，它处于运行状态；它本可以运行但没有空闲的 CPU 可用时，处于就绪状态；它在等待某样东西时，处于阻塞状态：一把锁、一个设备、一个信号，或某个时间点，有些内核把最后这种情况作为单独的睡眠状态来跟踪。新线程最初处于已创建状态，被启动后变为就绪；已结束的线程处于死亡状态，直到内核将其回收。只有就绪线程会争夺 CPU，调度器把它们保存在自己的运行队列中。这个名字是沿袭下来的：这种结构可以是 FIFO、按某个键排序的列表、堆，或者每个优先级一个队列，只要能让该策略以低代价选出下一个线程即可。

CPU 总得运行点什么，所以没有线程就绪时，它会运行一个空闲线程，空闲线程通常让核心停机，直到下一次中断。空闲线程绝不应阻塞，因为它身后再没有任何可以回退的对象。

陷阱在于正在运行的线程。它在运行期间是留在运行队列中，还是在被选中时移出、离开 CPU 时再放回，这只是一种约定；混用这两种约定的代码要么把一个线程入队两次，要么把它弄丢。入队两次的线程会得到两次运行机会，而在有序队列中，一个保持原位的过期条目会打乱排在它后面的所有线程的顺序。从队列中丢失的线程一直处于就绪状态，却永远不会被选中，从外部看就像卡死了一样。

在 Cosmos 中，这些状态就是 `SchedulerThreadState` 的状态：`Created`、`Ready`、`Running`、`Blocked`、`Sleeping` 和 `Dead`，策略从不修改它们。正在运行的线程通常不在运行队列结构中：`PickNext` 会移除它返回的线程，而离开 CPU 的线程只有在仍为 `Running` 时，才会在选择之后通过 `OnThreadYield` 回来。例外是一个已经阻塞、但在上下文切换把它从 CPU 上换下之前就被唤醒的线程：它在仍然运行时就已是 `Ready` 并已入队。对已经是 `Ready` 或 `Running` 的线程进行唤醒不起任何作用，但 `Created` 线程在首次运行之前一直保持该状态，因此 `OnThreadReady` 可能对它到达两次，必须防止第二次插入。空闲线程就是启动线程本身，即随后去调用内核的 `BeforeRun` 和 `Run` 的那个线程。`PickNext` 返回 `null` 时就运行它，无论它处于什么状态。内核的互斥锁、中断事件和条件变量（最后一个通过其底层管程支撑着 CoreLib 自身的等待：`Thread.Sleep`、`Thread.Join`、一个 `WaitHandle`）让它在两次检查之间自旋、轮询或停机，而不是挂起，因此它永远不会到达 `OnThreadBlocked`：一个被挂起的空闲线程会经由空闲后备以 `Running` 状态回来，却没有那次把票数还给它的唤醒。除此之外，它像其他任何线程一样经过各个钩子：安装了策略时，它到达 `OnThreadCreate` 时已经是 `Running`，被换出时则通过 `OnThreadYield` 回来。参见[生命周期](../scheduler.md#lifecycle)和[接口](../../user/scheduler-plugging.md#the-interface)。
