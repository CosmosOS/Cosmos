# 策略与机制

调度器要做两件不同的工作。机制（mechanism）负责执行：它保存离开 CPU 的线程的寄存器，恢复到来的线程的寄存器，维护现有线程的列表，并让每个线程在运行、等待和就绪之间转换。策略（policy）负责决策：下一个运行哪个就绪线程、运行多长时间，以及被唤醒的线程排在什么位置。把两者分开，就可以更换策略，而不必触碰那段必须完全正确、内核才能安然度过一次切换的代码；同一套机制也因此可以服务于公平份额策略、实时策略或简单的轮转。

两者之间的边界是一个接口。机制在若干固定的时机调用策略：线程被创建、变为就绪、阻塞、退出或用完时间时；在即将切换时，它还会向策略索取下一个线程。策略根据自己的簿记数据作答，从不亲自执行切换：它需要知道的一切都通过这些调用传入，它做出的一切决定都通过这些调用的返回值传出。

陷阱在于这条边界本身也带有规则。机制按它选定的顺序、在它选定的上下文中调用策略，并依赖一些必须由策略维持的不变式，例如绝不在队列中把同一个线程保存两次。一个在错误时机做出正确决定、或者保留了重复条目的策略，会像切换代码本身的 bug 一样必然地破坏机制，而且故障会在远离策略的地方暴露出来，表现为一个再也不会运行的线程。

在 Cosmos 中，策略是 `IScheduler`，这个接口仿照 Ekiben（一个可插拔的调度器 API）的 `EkibenScheduler` trait 设计；机制是 `SchedulerManager`。管理器维护线程登记表，设置每一个 `SchedulerThread.State`（策略可以读取状态，但从不写入），并接收定时器节拍，中断桩代码则负责保存和恢复寄存器；策略把自己的簿记数据保存在每个线程和每个 CPU 的 `SchedulerData` 槽中。启动时安装的策略是 Stride，内核可以在运行时通过 `SchedulerManager.SetScheduler` 安装另一个策略，该方法会把所有存活的线程移交给它。参见[概述](../scheduler.md#overview)和[接口](../../user/scheduler-plugging.md#the-interface)。
